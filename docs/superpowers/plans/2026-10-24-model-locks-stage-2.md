# Model Locks and Idle Reminder (Stage 2) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One person at a time holds a model for update, build or report; others see it read-only and are told when it frees up; forgotten sessions get an idle pop-up and a chime.

**Architecture:** A `model_locks` table (one row per model, keyed by `model_id`) written only through a lock service that the server checks on every start of update, build or report. A lock is taken with a conditional insert and released by the holder, by the job's end, or by an admin; no timer releases it. The web app polls a small lock-status endpoint on the model screen and on a light heartbeat, and shows the toast, read-only banner and idle pop-up from that state. The chime is a short Web Audio tone, gated by the user's Settings and the system's reduced-motion/sound preference.

**Tech Stack:** Python 3.12, FastAPI, SQLAlchemy 2 + Alembic, PostgreSQL 16, pytest; React + TypeScript, pnpm, Vitest, generated OpenAPI types (`pnpm api-types`).

**Spec:** [docs/superpowers/specs/2026-10-22-auth-roles-locks-design.md](../specs/2026-10-22-auth-roles-locks-design.md) section 8 (model locks), section 9 item 2, section 10 (screens), section 13 (owner decisions: 30-minute idle reminder, admins view read-only and see holders, admin can release any lock).

## Global Constraints

- Sessions expire after 9 hours of inactivity (stage 1, unchanged).
- Idle reminder after 30 minutes with no clicks or keys, and only when nothing of the user's is still running. Value lives in `config.py` settings, never a literal in code or tests.
- Starting update, build or report while another person holds the lock is refused by the server (HTTP 423 with holder name and time), not only hidden in the page.
- No timer releases a lock.
- The original workbook is never overwritten; every write is a new `model_versions` row; approval steps are unchanged. The lock decides who may start, nothing else.
- Admins may open any model read-only at any time and may release any lock; each release writes an audit entry naming the holder.
- Every route needs a signed-in user (`get_current` dependency). Lock tokens or identifiers never go in URLs beyond the model id.
- The chime is skipped under reduced-sound settings; the toast still appears. The pop-up and toast respect reduced motion (no animation, instant appearance).
- Money is not touched by this stage.

## Review Focus

1. Two people click "update" on the same model in the same second -> exactly one succeeds, the other gets 423; no double lock.
2. A holder's browser crashes mid-update -> the job's end still releases the lock; a crashed browser with no job leaves the lock held and the holder sees "You still have 1 model open" on next sign-in.
3. A job fails (exception) -> lock is released in a `finally`, not left held.
4. Model deleted or unlinked while locked -> lock row is removed with the model (FK cascade), no orphan.
5. Idle reminder while a background update is running -> no pop-up; pop-up after the update finishes if the user is still idle.
6. Reduced-sound / reduced-motion set -> no chime, no animation; toast still shows.
7. Lock release while a read-only colleague is on the page -> their view refreshes within one poll interval, buttons enable, toast appears only for those who opened it while locked.

Each line above gets its test in the owning task (Tasks 2, 3, 4, 5, 7, 8).

### Task 2: Lock service (acquire, release, status)

**Files:**
- Create: `analekh/locks/__init__.py`, `analekh/locks/service.py`
- Test: `tests/test_locks_service.py`

**Interfaces:**
- Consumes: `ModelLock`, `User`, `AuditEntry` (Task 1).
- Produces:
  - `class LockHeld(Exception)` with attributes `holder_name: str`, `activity: str`, `taken_at: datetime`.
  - `acquire(session, *, model_id: int, user_id: str, activity: str, job_id: str | None = None) -> ModelLock` - raises `LockHeld` if another row exists; re-entrant for the same user (returns the existing row, refreshes `last_seen_at`).
  - `release(session, *, model_id: int, user_id: str) -> bool` - deletes only when `user_id` matches; returns whether it deleted.
  - `release_for_job(session, *, model_id: int, job_id: str) -> bool` - used by jobs.
  - `force_release(session, *, model_id: int, admin_id: str) -> ModelLock | None` - writes `AuditEntry(action="lock.release", user_id=admin_id, detail={"model_id":..., "holder_id":..., "holder_name":..., "taken_at":...})`.
  - `status(session, *, model_id: int) -> ModelLock | None`.

Acquire uses `INSERT ... ON CONFLICT (model_id) DO NOTHING` and checks rowcount; on zero rows, reads the holder and raises `LockHeld`. This is the only place that decides who holds a lock.
