# Sign-in, Roles and Upload Limit (Stage 1) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every request is made by a signed-in user with a role; admins manage users, templates and the upload limit; the Welcome scroll leads to a sign-in screen; reset codes and alerts go out by email.

**Architecture:** A new `analekh/auth/` package (passwords, sign-in service, mail-backed reset) behind a `/auth` router. `deps.get_user` is replaced by a session-cookie lookup and every existing router requires it. One shared upload guard reads the limit from an `app_settings` row. The web app adds a Login view inside the Welcome screen and an admin Users page.

**Tech Stack:** FastAPI, SQLAlchemy 2 + Alembic, `argon2-cffi` (new), pytest; React + TypeScript, TanStack Query, pnpm.

**Spec:** `docs/superpowers/specs/2026-10-22-auth-roles-locks-design.md` (stage 1 = sections 4 to 7 and 9a, password sign-in only). Mockup: `docs/superpowers/specs/assets/login-calendar-mockup.html`. Stages 2 (locks) and 3 (Microsoft) are separate plans.

## Global Constraints

- Login is `POST /auth/login` with a JSON body. Email, password, session tokens, reset codes are never in a path or query string, and never logged (no request bodies, no `Authorization` or `Cookie` headers).
- Session cookie `analekh_session`: `HttpOnly`, `Secure` (except when `ENV=dev`), `SameSite=Strict`. Bridge and add-in send `Authorization: Bearer <token>`.
- Sign-in page responses: `Cache-Control: no-store`, `Referrer-Policy: no-referrer`.
- No SQL built from input: SQLAlchemy bound parameters only; no f-strings or `text()` with interpolated values in `analekh/auth/`.
- Passwords: argon2id; max length 128; error is always `Email or password is incorrect.`; an unknown email takes the same time as a wrong password.
- Failed sign-ins per account: 3 failures pause 5 minutes; 5 failures block password sign-in until reset (Microsoft accounts: admin clears). A successful sign-in resets the count.
- Sessions expire after 9 hours of inactivity; revoked on sign-out, password change and user disable.
- Reset: 6-digit code by email, single use, 2 minutes, stored hashed, own attempt limit (5); the "request" reply is identical for known and unknown emails.
- Upload limit: `max_upload_bytes` setting default 25 MB; ceiling `100 MB` (config `MAX_UPLOAD_CEILING_BYTES`); 413 message `This file is {size} MB; the limit is {limit} MB. Ask your admin.`; applies to new uploads only; each change audited.
- Development switch (owner, 2026-10-22): `AUTH_ENABLED=false` turns sign-in off and acts as the built-in admin `dev@analekh.local` (id = `default_user_id`, no password); it defaults to on, is honoured only when `ENV=dev`, and API start-up refuses it otherwise. The web app reads `GET /public/auth-status` and skips the sign-in screen when it is off.
- No hardcoded values (owner, 2026-10-22): thresholds, timings, limits, identities, addresses and credentials come from `Settings` in `analekh/config.py` (environment variables) or from the database; defaults live only in `config.py`. Code and tests read the setting rather than repeating its value. Protocol names (cookie name, CSRF header name) are named constants, not secrets. The upload default (25 MB) is a setting too.
- Roles are exactly `admin` and `analyst`. Only admins: upload/activate/retire templates, manage users, change the upload limit.
- Money stays Decimal; no changes to filings, XBRL or grounding code. Secrets only in environment variables.
- Run `uv run ruff check . && uv run ruff format . && uv run mypy analekh && uv run pytest -q` and `uv run alembic check` before each commit. Commit messages are given to the owner, who signs and commits (never run `git commit`).
- Web: motion only answers a click or gesture; screens appear at once; reduced motion respected; Inter, one accent blue, light and dark themes.

## Review Focus

- A 10,000-character password is refused quickly (400) without hashing it. Tested in Task 2.
- `" Kaushal@Firm.IN "` signs in as the same account as `kaushal@firm.in` and cannot create a duplicate. Tested in Task 3.
- Requesting a second reset code invalidates the first; 5 wrong codes burn the reset. Tested in Task 5.
- Disabling a user with a live session makes that session's next request return 401. Tested in Task 3.
- An expired session in the browser sends the user to sign-in and back to the page they were on, never to a blank screen. Tested in Task 10.
